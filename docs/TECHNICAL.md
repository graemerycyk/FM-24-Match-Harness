FM24 match-engine harness for macOS: technical notes
===

These notes describe how the macOS version works: `fm24ctl`, the launcher
that loads the harness into Football Manager 2024 24.4.2 from Steam, the
harness dylib and its job protocol, the build tables, the build and
FM24Viewer.app. For setting up and using it, see the [README](../README.md),
the [macOS guide](MACOS.md) and the [CLI reference](CLI.md).

The harness's job, match, fixture and seed-building code comes from the
original Windows project,
[PhilipArmstead/FM-24-Match-Harness](https://github.com/PhilipArmstead/FM-24-Match-Harness)
by Philip Armstead. Its Windows-specific parts (injecting a DLL into
`fm.exe`, the Windows memory, thread and profiler code, and the Win32
viewer) remain in the source, so the shared code stays mergeable with that
project, but they are not described or supported here. For Windows, use the
original project.

# How it works

## Loading the harness

The game is signed with the hardened runtime, which denies other processes
access to it, so nothing can be injected into a running game. The game is,
however, entitled to accept `DYLD_INSERT_LIBRARIES` and libraries signed by
others, so the harness is loaded when the game starts.

`fm24ctl install` (also `launch`, and any command that finds no harness)
writes the dylib, `fm24-harness-<version>.dylib`, and the launcher,
`launch-fm24.sh`, into `~/Library/Application Support/fm24-harness/`.
`install` prints the Steam launch option that runs the launcher,
`/bin/sh "<launcher>" %command%`. It writes a development build's dylib
from beside `fm24ctl` if there is one (as in `build/`), and otherwise the
copy built into `fm24ctl` (`src/runner/embedded_macos.c`). An identical file
is left alone. Otherwise a new file is renamed over the old one, so a game
that has the old one loaded keeps its own copy: overwriting it in place
would invalidate the code signature of its mapped pages.

Steam runs the launch option through `/bin/sh`, which drops `DYLD_*`
variables, so the launcher sets `DYLD_INSERT_LIBRARIES` itself and starts
the game executable, keeping the libraries Steam inserts for its overlay
(`STEAM_DYLD_INSERT_LIBRARIES`). On Apple silicon, Steam starts the launch
option as an Intel process, and a game started from it would inherit that
and run under Rosetta. The launcher therefore starts the game through
`/usr/bin/arch` in the same process, so Steam still tracks the game: with
the arm64 slice where `sysctl` reports Apple silicon, and the x86_64 slice
on Intel Macs, or under Rosetta when a waiting `launch --rosetta` has left
a request for it. The launcher also takes a waiting `launch --save`
request and passes the game its auto-play file (see
[Loading a save](MACOS.md#loading-a-save)). Without Steam's launch option,
`fm24ctl launch` starts the game directly with `open` (`open --arch x86_64`
for `--rosetta`), which has not been verified (see
[Known limits](MACOS.md#known-limits)).

## The harness

The dylib's initialiser runs before the game's own. In the game's process
(an executable ending in `/Contents/MacOS/fm`; helper processes that inherit
`DYLD_INSERT_LIBRARIES` are left alone) it only starts the job thread, with
a 16 MB stack, since jobs run engine code on it. The thread opens
`harness.log` next to the dylib, identifies the game by the `LC_UUID` of
the running slice (`src/common/macos_builds.c`), checks that the build
tables have every address it needs and that the first bytes of each
function it calls match (`src/dll/game_macos.c`), and opens the job socket.
It then logs `ready; waiting for jobs`, or `refusing jobs: unsupported game
build` and answers every job with an error. A `refusing: ...` line before
it gives the reason, such as an unsupported build's UUID or unexpected code
at a called function (a software breakpoint, or another build). The dylib
exports nothing.

## The job protocol

`src/common/protocol.h` is what the harness and `fm24ctl` agree on. The
channel is a Unix socket in your temporary directory (the one
`getconf DARWIN_USER_TEMP_DIR` prints), named after the protocol version:
`fm24-harness-<version>.sock`. The harness holds an exclusive lock on
`fm24-harness-<version>.sock.lock` while it serves, so `fm24ctl` can tell a
running harness from a socket left behind by a game that crashed, and a
second game process with the same version stays idle. It binds the socket
under a temporary name, open only to your user, renames it into place, and
removes it when the game exits normally.

The harness runs one job at a time:

1. `fm24ctl` connects. Both sides check that the other end belongs to the
   same user (`getpeereid`). Runners that connect while a job runs wait in
   the socket's backlog; while the backlog is full, `fm24ctl` retries as
   long as the harness holds its lock.
2. The harness sends one byte, `+`, when it takes the connection.
3. `fm24ctl` writes the job, `key=value` lines such as `command=status` (at
   most 16384 bytes; `src/dll/job.h` lists the commands), and shuts down
   its sending side. The harness waits up to 60 seconds for the whole job.
4. The harness runs the job (`job_execute`), replies with one result line
   starting with `ok` or `error` (at most 512 bytes), and closes the
   connection.

Jobs carry full paths, so a runner works with a harness loaded from any
folder. `fm24ctl` writes job inputs into the same temporary directory,
which the game can always read. A `fm24ctl` of another protocol version
finds no socket of its own: it reports the version the game has loaded and
says to restart the game (unit tests cover finding the other version's
socket; the message has not been checked with the game).

## Build tables

The harness names game functions, data and serialiser call sites by the
RVAs of the Windows Steam build, as the original project does
(`src/dll/game.h`, `sites.h`, `site_members.c`), and labels every field of
a serialised match from the call stack of the write that produced it. The
macOS build is compiled by clang with the Itanium C++ ABI: its code is laid
out, inlined and tail-called differently, and many objects are laid out
differently (libc++ containers are smaller than MSVC's). The harness keeps
all its logic and adds per-architecture tables
(`src/dll/game_macos_tables.c`, see `src/dll/game_macos.h`):

- `addresses`: the macOS counterpart of each RVA the harness calls or
  reads (functions, vtables, globals), and the game state objects that
  `status` reads (`MacosGameData`).
- `frames`: for every return address in the macOS serialisers, the Windows
  frames it stands for. One macOS frame may stand for several Windows
  frames (a call clang inlined) or for none (a call MSVC inlined or turned
  into a jump). The write trace translates each macOS stack this way, so
  the labels, member names, per-seed alignment and team replacement work
  unchanged. A frame without a Windows counterpart keeps its own identity
  (`0x80000000 | macOS offset`).
- `signatures`: the first bytes of each function the harness calls,
  checked at startup.
- The thread-local PCG32 the pre-match setup draws from.

The macOS object layouts are in `src/dll/game.h`. The tables are generated
from `tools/macos/steam-24.4.2.json`;
[`tools/macos/README.md`](../tools/macos/README.md) describes the mapping,
how it was made and how to check it against the installed game.

# Building

Requirements: macOS 11 or newer with the Xcode Command Line Tools (Apple
clang and Swift), CMake 3.20 or newer, and Ninja if it is installed
(otherwise Makefiles). `format.sh` and `tidy.sh` need clang-format and
clang-tidy 22 or newer from Homebrew's LLVM (`brew install llvm`). See
[Development](DEVELOPMENT.md#macos) and `scripts/env.sh`.

```sh
scripts/build.sh     # build into build/, install fm24ctl, the viewer and tests into bin/
scripts/format.sh    # apply .clang-format (--check to only verify)
scripts/tidy.sh      # clang-tidy with .clang-tidy per architecture (warnings are errors)
```

The build script always configures Release mode and C17, including all
regression checks in `fm24_tests`. It builds universal (arm64 and x86_64)
binaries for macOS 11 and newer with Apple clang, and the viewer for macOS
13 and newer (see [The fixture viewer](DEVELOPMENT.md#the-fixture-viewer)).
CMake defaults Release builds to `-O2 -DNDEBUG`, with link-time
optimisation across the shared code, dylib, runner and tests. Configuration
fails if the compiler does not support LTO. Release links discard unused
sections (`-dead_strip`). The dylib is compiled with hidden visibility and
exports nothing. Frame pointers are kept (`-fno-omit-frame-pointer`),
because the trace and the profiler walk frame-pointer chains. Debug builds
retain their normal flags without LTO. Fast-math and
build-machine-specific CPU instructions are not enabled.

Unstripped binaries stay in `build/` for diagnosis. `fm24ctl` embeds
`build/harness-embedded.dylib`, a stripped (`strip -x`), ad-hoc signed copy
of the universal dylib, in its `__TEXT,__fm24_harness` section, so `bin/`
holds no dylib (the script deletes any left there, since a loose dylib
beside `fm24ctl` would override the built-in one). The script installs
copies into `bin/`, then strips `fm24ctl` and `fm24_tests` and signs them
again ad hoc: stripping invalidates the linker's signature, which arm64
requires. Installation, stripping or signing errors fail the script instead
of silently leaving old binaries in `bin/`. For a harness the game has
loaded, see the protocol-version notes below.

Run `bin/fm24_tests` for the application regression checks, or pass a suite
name (`job`, `dll`, `job_run`, `common`, `fixture_data`, `runner`,
`runner_main`, `batch`, `fixture_export`, `fixture_view`, `player_inject`,
`fixture_lineup` or `macos`) to run only that suite. On Apple silicon with
Rosetta, `arch -x86_64 bin/fm24_tests` runs the x86_64 slice's.
`fm24_tests` needs its two stand-ins next to it (`fm24_stand_in_game` and
`libfm24_stand_in_library.dylib`). Each named test prints `[PASS]` or
`[FAIL]`, followed by a test/failure count; failures return a nonzero exit
code. Assertions report the source location, expression and expected and
actual values without stopping the remaining checks.

The `dll` suite uses synthetic engine objects to check serialisation traces,
edit alignment, player identity across rebuilt line-ups, instruction labels
and UTF-8 exports without loading FM24. It also reads a synthetic game's
state: the status line, the save name's checks, the refusal of jobs while
the game is busy, and the save and date in exports but not in decoded
fixtures. The `job` suite also covers repeated seed keys, malformed or
overflowing seed values and status jobs.

The `dll` suite's synthetic matches have every kind of squad slot (a starter,
substitutes brought on, off, injured or sent off, one not used, a slot
without a person, a negative rating). It checks the `--detailed` averages
against text written before the per-match rows were added, and the
per-match rows against `tests/synthetic_rows.py`, which computes them
independently (`python3 -I tests/synthetic_rows.py rows 42 37000
4210832071`). The `job_run` suite runs `src/dll/job_run.c` with fake engine
calls on those matches: results and files are byte-identical to the run job
before protocol 1.4.0 without its keys, rows stay in list order however the
workers finish, every main row on disk has its other rows on disk at every
flush, and it checks skipped seeds, the stop file, write failures, the
report and its longest line, and that the per-match rows average to
`--detailed`'s values.

The `runner` suite checks single-read config preparation, CLI and CSV numbers,
result-file failures, `status`'s exit codes, configs with and without `save`
and `game_date`, the check of a job's save (what happens in each state of
the game, the arguments before and after the save options, and the commands
that read a fixture's save), the replacement of an installed dylib and
`probe` on synthetic universal and single-slice files, without connecting
to FM24. `runner_main` checks the conversion of arguments, the commands'
dispatch and opening fixtures in the viewer app, and `macos` which images
of the game the harness accepts, its refusal of jobs elsewhere, finding
another harness version's socket, the direct start's `open` command, how
`launch` judges the starting game, and a command's save check against a
stand-in harness.
Config preparation reads replacement-team metadata while encoding, rather than
loading and parsing the same JSON twice. Field visitors reuse one field buffer
instead of retaining the entire encoded fixture. Strings and hex values are
copied in batches, and discarded annotations allocate no decoding buffers.
Malformed UTF-8, Unicode escapes, hex digits and replacement IDs are rejected.

The `batch` suite checks plans and their refusals, the scatter generator's
golden values and that it is a bijection, chunks and both orders, part jobs
and their size cap, the verifier on torn, zero-filled and inconsistent
files, the merge, the part chain, and batches run to the end through every
kill and restart (see [Batches](#batches-fm24-batch-plan1)), with a fake
host in place of gzip and the disk's syncs.

Per-seed rebuilding omits write tracing and edit alignment when the input
has no edits. Edited inputs with unchanged write sites skip call-chain
parsing and alignment allocations. When tracing is needed, call chains are
interned as numeric RVAs (after the [build tables](#build-tables)'
translation); their text is formatted only once per distinct chain. CPU
timing calls are limited to the profiled worker, and workers only copy the
input when patching seeds rather than rebuilding it.

Use `ctest --test-dir build --output-on-failure` for individual results and
the release checks. Building does not run the tests. The `release` check
(`tests/release_macos_test.cmake`) verifies both slices, the signatures,
the embedded dylib and that nothing is exported; on Apple silicon with
Rosetta, `x86_64` runs the tests' x86_64 slice, and the viewer has its own
checks (see [The fixture viewer](DEVELOPMENT.md#the-fixture-viewer)). To
stage only the distributable runner, without the test executable:

```sh
cmake --install build --config Release --prefix dist --component Runtime --strip
```

Sign the staged runner again, as `scripts/build.sh` and the release check
do: the linker signs only the arm64 slice, and `codesign --verify` fails on
a universal binary whose x86_64 slice is unsigned.

```sh
codesign --force --sign - dist/fm24ctl
```

The build uses `-Wall -Wextra -Wpedantic -Wshadow -Wconversion` and friends
and is warning-free; `format.sh --check` and `tidy.sh` are clean.

When configuring CMake directly, use `-DFM24_BUILD_TESTS=ON` to include the
test executable. Its portable reader, filename and player-injection checks
can also be built on their own, without CMake:

```sh
cc -std=c17 -O2 -Isrc/common -Isrc/runner -Isrc/ui \
  tests/test.c tests/fixture_data_test.c tests/fixture_export_test.c \
  tests/player_inject_test.c src/ui/fixture_export.c \
  src/runner/fixture_data.c src/runner/player_inject.c \
  src/runner/match_config.c src/runner/json_reader.c \
  src/common/buffer.c src/common/tactic_names.c -o /tmp/fm24_tests
/tmp/fm24_tests
# Optional integration check against the local Aston Villa/Bristol City baseline:
/tmp/fm24_tests fixture_data tools/experiments/baseline.json
```

Tests use the same dependency-free framework as the Triple Triad project:
include `test.h`, define cases with `TEST(describes_the_behaviour)`, and
use `ASSERT_INT_EQ(actual, expected)` or `ASSERT_BOOL_EQ(actual, expected)`.
Register each case with a descriptive `test_run` call in its suite's
`register...Tests` function. Guard failed setup before dereferencing pointers
or inspecting buffers, since assertions do not abort the test. Keep
pointer-sized and 64-bit comparisons in `ASSERT_BOOL_EQ` to avoid narrowing
them to the integer assertion's `int` parameters.

**Rebuilding while the game runs:** the game loads the harness only when it
starts, so a rebuilt harness loads when the game next starts; until then,
commands use the harness the game loaded without saying so, unless its
protocol version differs. `build/fm24ctl install` (or `launch`) installs
the build's unstripped `fm24-harness-<version>.dylib` from `build/` rather
than its embedded copy. To give a rebuilt harness its own socket and file
name, bump `HARNESS_PROTOCOL_TEXT` in `src/common/protocol.h` and build;
CMake re-configures by itself.

**Generated code:** after changing an address in `src/dll/game.h`,
`sites.h` or `site_members.c`, update its macOS counterpart in
`tools/macos/steam-24.4.2.json` and run
`python3 -I tools/macos/gen_tables.py tools/macos/steam-24.4.2.json src/dll/game_macos_tables.c`
(see [tools/macos](../tools/macos/README.md)).

# The viewer

FM24Viewer.app is an AppKit shell with SwiftUI views (`src/ui/macos/`) over
the viewer's rules in portable C (`src/ui/fixture_view.h`, which Swift
imports through `src/ui/module.modulemap`). Those are the rules of the
original Windows project's viewer, so the summary, squad lists, edits and
venue values follow the same rules. It uses only the system's AppKit and
SwiftUI, with no third-party UI or parsing dependencies. It reaches the game
by running its own copy of `fm24ctl` (`get-next-fixture`, `decode`, `run`,
`replace-home`, `replace-away`, `inject-player`, `list-teams`,
`list-players`, `launch` and `install`), with every path the game reads or
writes in your temporary directory, and takes the first line of `fm24ctl`'s
explanation when no harness serves the job socket.

Opening a fixture does not change its source;
`fm24ctl <fixture.json|fixture.bin>` opens it in the `FM24Viewer.app`
beside `fm24ctl` and leaves the other commands unchanged. Viewing a JSON
file does not connect to the game. A `.bin` fixture is decoded by
`fm24ctl decode`, through the `inspect` job, from a copy in the viewer's
own temporary folder (`fm24-viewer-<pid>`). Inspection deserialises and
traces the existing match without running preparation, building another
fixture or invoking the engine's match runner. Started without a fixture,
the viewer exports the next fixture to `temp-fixture.json` in the
temporary directory and shows it as not yet saved; if the export fails,
the window stays open and says why. The export link in the summary, or
**File > Export**, writes an unsaved fixture with its edits to the export
folder, never replacing an existing file.

The Venue tab edits labelled venue values. Float values are bit-copied
to/from their serialized `u32` representation. The config visitor exposes
numeric source spans so venue saves can patch only the values, retaining
unrelated fields, annotations and team replacement IDs. Shared validation
rejects invalid dimensions, coordinates, surfaces, condition and capacity
relationships. The same writer derives pitch geometry and every attendance
copy for saving, exporting, team replacement and simulation. Saves replace
the destination only once the whole file is written. Unstored edits are
marked in the summary, and opening another fixture, closing or quitting
asks before discarding them.

The Simulation tab runs `fm24ctl run`. Thread bounds reuse the CLI default
(logical CPUs minus one, clamped to 1-16). Seed patterns are limited to 255
characters, checked for job-safe characters before submission, and fully
parsed by the harness. The viewer always plays a copy in its temporary
folder, with venue values and pending player edits written into it and the
results written there too, so the source is never overwritten by
simulation. The harness does not report progress, so the viewer reads the
results CSV every 200 ms: the run flushes each row as the rows complete in
seed order, so the count trails by at most one match per thread less one,
and a line that is not a result leaves the bar indeterminate. The Dock
icon's badge shows the percentage, and an `NSProcessInfo` activity keeps
the Mac from idle sleep and the viewer out of App Nap while the run lasts.
Afterwards the viewer moves the results (and detailed reports) beside the
fixture, following the CLI's fixture-based naming and replacing earlier
ones, or into the export folder for a fixture not yet saved. A run that
fails part way has its rows so far saved, as the game leaves them.

The team picker (a popover from the pencil) and the swap prompt (a sheet)
follow the rules of the original Windows project's viewer
(`Model/Choices.swift` and `Model/Replacement.swift`), whose tests mirror
that viewer's. The viewer loads the team list (`fm24ctl list-teams`) in the
background the first time either team is edited, to fill its filterable
picker; a picked team is
submitted by ID, so clubs that share a short name resolve. It loads the
player list (`list-players`) the first time its swap prompt opens. "Swap
player" swaps out the side's selected row, and is enabled only while
exactly one player is selected. The prompt's label names that player
("Swap <name> for..."). The new player field lists matches once 3
characters have been typed and the typing has paused for 100 ms. Matching
ignores case and accents: the folding decomposes the text, spells out the
letters Æ, Ð, Đ, Ø, Þ, ß, Ħ, ı, Ł and Œ, drops the marks that are not
letters and lowercases it, so "odegaard" finds "Ødegaard", and a name that
starts with the text comes first. Lists are sorted by that folded label.
Labels show the common name first, e.g. "Pelé (Edson Arantes do
Nascimento)". A picked label is injected by the ID at its end. Digits are
taken as a unique ID, which also works while the list is loading or if it
failed. The prompt's "Allow duplicates?" box passes `--allow-duplicate`, so
a player already in the fixture can be swapped into another block. Without
it, the refusal's hint points at the box. A replacement or swap writes the
fixture's JSON with the edits it carries (a `.bin` fixture's JSON decoded
when it was opened) into the viewer's temporary folder, has `fm24ctl` work
there and writes the venue values into the result. The lists are dropped
when the game quits, since another save may list others.

# Use

Run `fm24ctl` from `bin/` (or the release folder): it opens the
`FM24Viewer.app` beside it. `harness.log` lives next to the dylib the game
loaded, in `~/Library/Application Support/fm24-harness/`. A runner sends
its job over the socket of its protocol version, so a `fm24ctl` in another
folder (e.g. `build/`) with the same protocol version uses the harness the
game loaded, and its log.

The harness runs one job at a time. Runners (the viewer's included) that
submit while a job is running wait for it (`the harness is running another
job; waiting for it to finish`), and their time limit includes that wait.
A runner that times out stops waiting but does not cancel the harness's
work; later jobs still wait for it.

1. Start FM24 with the harness (from Steam, with the launch option
   `fm24ctl install` prints, or with `fm24ctl launch`) and load the save,
   or let `fm24ctl launch --save <save>` load it. Wait until the game is
   **idle** (not processing). The engine calls aren't synchronised with the
   game's own threads. The harness refuses jobs while the game loads or
   processes a game (see step 7).
2. Every command that needs the game connects to the harness's socket
   first. If no harness of this version serves it, the command installs
   this version's dylib and launcher (see
   [Loading the harness](#loading-the-harness)) and says whether the game
   is not running, has another harness version loaded or runs without the
   harness, and how to start it with the harness: a running game cannot
   load it. `harness.log` should say `ready; waiting for jobs`.
   `refusing: ...` means a different game build, or a software breakpoint
   on a called function. Old versions collect in the harness folder (see
   [Files and removal](MACOS.md#files-and-removal))
3. `fm24ctl run <input> [seeds] [out.csv]`,
   where `<input>` is a `.bin` input or a `.json` config; e.g.
   `fm24ctl run next.json` plays the config's own seed into `next.csv`.
   It prints a result line (`ok: N/N runs...` or `error: ...`) and a
   summary
	- seeds: `keep` (the input's own seed; the default), `42`, `1-1000`, or
	  `1,5,10-20`. A seed plays exactly as the game would with that seed
	  (`GAME_MATCH__init_from_fixture`'s seed): the seed also draws pre-match
	  values (attendance, the officials' match-day ratings, a random number
	  per player, weather), so for each seed `run` has the game rebuild the
	  input's fixture with that seed and re-applies the input's edits. An
	  unedited dump then matches the game; edited fields keep your values.
	  This needs the input to be the human manager's next fixture in the
	  running game (built in the current game state); otherwise `run` stops
	  with an error. To compare with the game, dump the fixture after clicking
	  "Simulate Match" and before "Continue", and run it before "Continue":
	  until the team is submitted, a build picks the human side's line-up
	  itself, differently for each seed. If a seed's build has a different
	  structure (another line-up or AI tactic) where the input was edited,
	  that seed fails (see `harness.log`). The input and the build are
	  aligned part by part along the serialiser's call chains (`align()` in
	  `seed_build.c`), so a difference only stops edits inside the parts that
	  differ. Each team's players are paired by person, not by place
	  (`comparePlayers` and `alignPlayers`), because the game can list them in
	  another order (see [Known limits](#known-limits))
	- `--keep-build`: play the input as it is, changing only its seed. The
	  pre-match values stay those of the seed it was built with, so results
	  differ from the game's for other seeds, but it works for any input
	- output: the input's name with a `.csv` extension unless given. An
	  argument of only digits, `,` and `-` is read as seeds, so name the output
	  e.g. `2024.csv`, not `2024`
	- matches run in parallel: by default on one worker thread per logical
	  CPU less one, at most 16. Results are identical whatever the thread
	  count (see the observers in [Known limits](#known-limits)), and rows
	  stay in seed order. In the original Windows project one match took
	  about 3 s, ~0.4 s per match on average with 11 threads on a
	  6-core/12-thread CPU, and each match's `ms` rose to ~4-5 s under load
	- `--threads N` (1-16): set the worker count (1 = one match at a time)
	- `--profile <samples.txt>`: sample the engine's stack about every 1 ms
	  (worker 0 only; see `src/dll/profiler.h` for the format). The first
	  line, `# fm <base>`, is the address of the running slice's Mach-O
	  header: an address in the game minus the base is its offset in that
	  slice, and adding `0x100000000` to the offset gives the unslid address
	  that `tools/macos/steam-24.4.2.json` uses. That file covers only the
	  functions the harness calls and the return addresses in the game's
	  serialisers, so most samples are not in it
	- `--detailed`: also write `<output>-players.csv` and `<output>-teams.csv`,
	  with each statistic averaged per match over all the seeds. Players (both
	  squads, substitutes included): appearances, starts, minutes, average
	  rating (over appearances), then goals, assists, shots, on target,
	  blocked and long shots, xG, xA, key passes, clear-cut and half chances,
	  passes (and progressive passes), crosses, dribbles, tackles,
	  interceptions, clearances, blocks and shots blocked, pressures
	  (attempted, inferred; completed), headers, fouls
	  committed and suffered, offsides, cards, set pieces taken, goalkeeper
	  saves, goals conceded, possession won and lost, high-intensity sprints
	  and distance (km). Teams: goals, possession, average rating (as the
	  game's match statistics screen shows it) and the team totals. The data
	  is the engine's own per-player stats objects. The values match the
	  game's statistics screens, team and player (checked on one match, in
	  the original Windows project). The members are listed in
	  `src/dll/match_stats.c`. Player rows are ordered by unique ID and
	  retain each person's totals when a rebuilt line-up changes order or
	  introduces another player.
	  Reports are written only after every seed succeeds; a CSV or detailed-report
	  write failure makes the job fail rather than reporting success.
	- `--per-match`: also write every match's rows, unaveraged:
	  `<output>-match-players.csv` (one row per squad slot) and
	  `<output>-match-teams.csv` (one per side). See
	  [Per-match rows and run reports](#per-match-rows-and-run-reports-protocol-140)
	- `--keep-going`: a seed whose rebuild fails gets a row in
	  `<output>-failed.csv` and the run goes on; other failures still stop it
	- both teams' in-match changes (substitutions etc.) are made by the game's
	  AI, as when the game simulates a match nobody watches. Before kick-off
	  the harness resets the human manager's control flags to "no match plan,
	  not in control", so the Match Plan of whoever built the input doesn't
	  carry over. AI-managed teams are left as they are
	- `--human-control`: keep the input's flags instead. A team built with a
	  human in control then makes no tactical changes (nobody is there to make
	  them) and may not even replace injured players
4. `fm24ctl get-next-fixture <out.json|out.bin> [--seed N] [--full]` builds
   the human manager's next fixture (~0.2 s). The seed defaults to a clock
   value, like the game. The same seed gives a byte-identical file, because
   the seed also seeds the thread-local RNG the pre-match setup uses. Only
   the match's observers can differ, because they also depend on earlier
   builds (see [Known limits](#known-limits)); with other observers, a
   `--full` export's `paths` and `p` numbers differ too.
	- `--full` (JSON only): also write the research keys: `bytes` and `paths`
	  in the header, and `site`, `p` and `member` on each field. Without it
	  the file keeps only the values and the labels (`name`, `player`,
	  `flags`, `role`), about 1.5 MB instead of 5.4 MB. Both encode to the
	  same `.bin`
5. `fm24ctl encode <in.json> <out.bin>` converts a config to a `.bin` input
   (no game needed).
   `fm24ctl decode <in.bin> <out.json> [--full]` converts back through the
   `inspect` job the viewer opens a `.bin` with (`src/dll/job_inspect.c`):
   the game deserialises the input and the harness traces its serialisation,
   as for an export, but nothing is prepared, built or played. The config's
   `source` notes that it was decoded, and `--full` adds the research keys as
   for an export.
   `fm24ctl list-teams <out.txt>` writes `uniqueId<TAB>short name` lines for
   every club's first team, the teams `database_findTeam` resolves names to
   (`database_listTeams`, ~1 s).
   `fm24ctl replace-home|replace-away <in.json> <team> <out.json> [--full]`
   rebuilds either side (`src/dll/job_replace.c`). `<team>` is a
   `db::TEAM` unique ID or a club short name (`database_findTeam`). The
   input's edits are re-applied as in `run`, except those to the replaced
   team. If the input marks the other side's line-up as changed, `fm24ctl`
   then puts that side's players back in the input's places offline
   (`keepLineup` in `commands.c`, through `fixtureLineup_byPeople`), as the
   build lists them in the game's order; before the job it checks that
   output as a file it opens itself (`checkOutput` with `opened`). The
   output's `home_team`/`away_team` headers preserve both sides'
   overrides for later replacements and per-seed builds. For each build the
   seed builder swaps the teams in three places and restores them afterwards
   (`swapTeams` in `seed_build.c`):
	- the fixture's home (`+0x08`) and away (`+0x10`) pointers;
	- the copies of the fixture among the human's matches
	  (`[RVA_HUMAN_MATCHES_HOLDER]+0x130`). Without these the builder doesn't
	  give the human manager control and picks the human's side itself;
	- each original team's next-match opponent (`TEAM+0xA0` -> `+0x38`).
	  All required pointers are collected before mutation; exceeding the fixed
	  swap capacity fails without changing the game.
	  `fm24ctl get-player <person uid> <out.json>` writes a player's database
	  values as an `fm24-player/1` file (`src/dll/job_player.c`): the fields a
	  player block copies from the database, named by their block suffix, with
	  the age on the human manager's next match day. The player record is found
	  from the person through the Itanium RTTI (`database_playerRecord`): the
	  person's vtable gives the offset to the complete object and the mangled
	  class name, `N2db13ACTUAL_PLAYERE` or
	  `N2db28ACTUAL_PLAYER_AND_NON_PLAYERE`. For all 47 players of one
	  fixture, every value matched the fixture's (checked in the original
	  Windows project).
	  `fm24ctl inject-player <in.json> <home|away>.player[N] <uid|player.json>
		<out.json> [--allow-duplicate]` patches those values into one block offline
	  (`src/runner/player_inject.c`), fetching them first when given a unique
	  ID. Like a venue save, it replaces only value tokens (and the block's
	  `player` note) through the visitor's source spans, so the structure and
	  every other byte stay as they were.
	  `fm24ctl lineup <in.json> <home|away> [<player> <player>|<list>
	  <out.json>]` shows a side, or moves its player blocks to new places
	  offline (`src/runner/fixture_lineup.c`): it finds each block's span
	  through the visitor's object spans, writes the blocks in their new order
	  with their names' numbers replaced, points the other side's marking of a
	  moved player at its new place, and adds the header's `<side>_lineup`
	  marker (`ConfigOrigin.lineup`), which `run` warns about and `batch
	  create` refuses without `keep_build=1`. It then checks that the result
	  encodes to the same length and reads back with each place holding its
	  player. The viewer's core (`src/ui/fixture_view.c`) can keep a
	  pending order beside the Max edits, which still name the players'
	  blocks as the file has them, and then lists each place's slot with the
	  player the order puts there. A save (`fixture_edit.c`) applies the Max
	  edits, then the order, then the venue, and `fixtureView_commitOrder`
	  then renumbers the view's blocks to their new places, where the
	  viewer moves the selection too. Its Edit line-up sheet
	  (`Model/Lineup.swift`) sets the order by exchanging players, and
	  `PlayerChanges` carries it with the Max flags into every save, export,
	  replacement and simulation copy. A swap gives `inject-player` the
	  place the order gives the selected player, in an input with the
	  order written in, and refuses an ID of the side's own squad itself; a
	  team replacement drops the replaced side's order and, if the other
	  side's was changed or marked, makes the order that puts its players
	  back by unique ID pending again (`fixtureView_orderByPeople`), which
	  is none once `replace-home` or `replace-away` has done it in the file.
	  `fixtureLineup_byPeople` gives a missing person's place to the first
	  player no person names, so the others keep theirs. A simulation whose
	  line-up is changed or marked asks before it rebuilds each seed.
	  `fm24ctl list-players <out.txt>` writes `uniqueId<TAB>forename<TAB>
	  surname<TAB>common name<TAB>club short name` lines for every person with
	  a player record (`database_listPlayers`; the common name and the club
	  are empty when the player has none). A person's names are relative to
	  its `ACTUAL_PERSON_BASE` part, which `database_personFields` finds
	  through the vtable; the common name is at `+0x38` there. The viewer's
	  use of these lists is under [The viewer](#the-viewer).
6. `fm24ctl probe [path to fm.app]` reads only the `LC_UUID` of each slice
   of the game's executable and reports whether this harness supports it.
   It reads the file only: the game isn't needed (without a path it probes
   the running game's file, or the one in your Steam libraries). It prints
   each slice's UUID, writes no file, and exits with 1 for an unsupported
   build. A new build needs a new mapping (see [Build tables](#build-tables)).
7. `fm24ctl status` submits the `status` job, added in protocol 1.3.0
   (`src/dll/job_status.c`). It reads the game's state without writing
   anything (`src/dll/game_state.c`, through the fault-tolerant reads of
   `memory.h`) and answers with one line whose keys keep this order:
   `ok: <state> in_progress=0|1 processing=0|1 kind=N people=N
   human_team=0|1 menu_seen=0|1 autoplay=0|1 autoplay_read=0|1
   date=YYYY day D HH:MM save=<name>`. A date or save that cannot be read
   is left out, and the save runs to the end of the line. The runner exits
   with 0 for `ready`, 3 for another state and 1 without an answer. The
   objects it reads are `MacosGameData` in `src/dll/game.h`, with each
   slice's address in the mapping:
	- `in_progress`: u8 `game_options+0x5d`. The core loader sets it when a
	  load succeeds, just before it posts `LGOK`; a new game sets it too, and
	  leaving the game clears it.
	- `processing` and `kind`: `GAME+0xb8` (u8) and `+0xbc` (i32).
	  `GAME::start_processing` sets them to 1 and its argument, and
	  `end_processing` to 0 and -1. The game's code on disk suggested that
	  the start screen's auto-play load (`--auto_play_game_file`) does not
	  call `start_processing`, but in the game (arm64) that load read as
	  processing, kind -1, from "in progress" until it was idle. Each day of
	  **Continue** is processing of kind 1.
	- `people`: the length of the people list (`RVA_PEOPLE_LIST`, `+0x88`),
	  which the game's own auto setup checks. `human_team`:
	  `database_findHumanTeam`, a pass over the people, so it is looked for
	  only while a game is in progress and idle.
	- `menu_seen`: the pointer the start screen's first entry sets once the
	  game's auto setup, and so any auto-play load, has returned (arm64
	  `0x100c44698`, x86_64 `0x100cbe4fe`). Only `fm::APPLICATION`'s
	  shutdown clears it again (arm64 `0x100221690`, x86_64 `0x10022f12e`).
	- `autoplay`: `GAME+0x64`, set by the constructor and cleared when there
	  is no auto-play file; `autoplay_read`: `GAME+0x80`, the file's parsed
	  JSON.
	- `date`: `RVA_CURRENT_DATE` while a game is in progress, written as a
	  fixture's date (`gameState_formatDate`).
	- `save`: the string object at `[SAVE_SYSTEM]+0x28` (a u32 length, then
	  the bytes), which the game's loads set: kept only as valid UTF-8 text
	  of 1-255 bytes (`configWriter_isText`), without a trailing `.fm`.
	  In the game (arm64) it was the save's file name, for saves loaded by
	  `launch --save` from `cloud/games` and from another folder; a load from
	  the game's menu has not been checked.

	 The state is `busy` while processing, `loading` while people are loaded
	 but no game is in progress, `starting` or `menu` (before and after the
	 start screen) with neither, and `ready` or `no_team` once a game is in
	 progress, with or without the human manager's team. A game in progress
	 without `menu_seen` is `loading` too: the auto-play load sets
	 `in_progress` before its last steps, which the start screen's first
	 entry finishes on the main thread. Before any other job, `job_execute`
	 reads the state (without the team search) and refuses the job while the
	 game is `loading` or `busy`:
	 `error: FM24 is busy (loading); wait until it is idle`, or
	 `processing kind N`. A game that starts processing just after the check
	 still races the job.

CSV columns: `seed, home_goals, away_goals, clock_ticks (4/s), finished,
rng_final, ms`.

## Per-match rows and run reports (protocol 1.4.0)

Protocol 1.4.0 adds five keys to the `run` job, for per-match data and for
`fm24ctl` to supervise long runs. A job without them gets the same result
line and files as under 1.3.0. A malformed value fails the job
(`error: cannot read the job`). `runJob_format` (`src/runner/run_job.c`)
sends them after the other keys, only when they are set.

| Key | Values | Effect |
|---|---|---|
| `per_match` | `0` (default), `1` | Write `<stem>-match-players.csv` and `<stem>-match-teams.csv` |
| `index_base` | A decimal u64, `0` by default | The `index` of list place *p* is `index_base + p`; the job is refused if the last index would not fit in 64 bits |
| `seed_errors` | `stop` (default), `skip` | `skip`: a seed whose rebuild fails (`seedBuilder_build`) gets a row in `<stem>-failed.csv` and the job goes on. Load and statistics failures still stop it |
| `stop_file` | A path | Before taking each seed, a worker checks whether the file exists. Once it does, no seed starts, the ones already started finish, and the job reports `stopped by the stop file` |
| `report` | `0` (default), `1` | Append the report below to the result line |

`<stem>` is the output path without `.csv` (`matchStats_siblingPath`). The
new files get their headers when the job opens them, even if no rows
follow; the main CSV is the same in every mode. [Per-match
rows](CLI.md#per-match-rows) lists the columns.

**Statistics.** `matchStats_read` (`src/dll/match_stats.c`) reads a played
match once into a `MatchStats` (about 17 KB, one per worker, no lock): each
slot's identity, minutes and raw values, with the minutes, appearances and
possession computed as for `--detailed`. `--detailed` adds it to its totals
under the run's lock (`matchStats_accumulate`, rounding each value to 2^-20
as before), and `per_match` formats its rows outside the lock
(`matchStats_formatRows`). Both take their team values from
`computeTeamValues`, rounded for the totals and raw for the rows. Ratings
are signed hundredths written exactly (`-0.05`); `xg`, `xa` and the
distance in km use `%.9g`, which tells every f32 apart.

**Write order.** Rows are written in list order, as the seeds before them
finish. `writeReadyRows` (`src/dll/job_run.c`) does it in two steps, with
the run's lock held: first the per-match rows and failed seeds of every
seed now ready, flushed; then those seeds' main CSV rows, flushed. So a
main row reaches the system only after its match's other rows and every
earlier failed seed's row. A game that stops loses only what stdio had
not written, and leaves a consistent prefix. The harness does not sync to
disk; after a power loss, a reader must check the files against each other.

**Result line.** It is unchanged unless something new happened:

```text
ok: 1000/1000 runs, 3 skipped (rebuild failed), each seed rebuilt by the game
error: 412/1000 runs, stopped by the stop file, each seed rebuilt by the game
```

The first count includes skipped seeds. A stop file that appears once every
seed has started stops nothing, and the job is `ok`. With `report=1`, the
line ends with `; report ` and these keys, in this order (on one line,
wrapped here):

```text
protocol=1.4.0 commit=<40 hex digits> dirty=0 build=2081827 slice=arm64 translated=0
pid=81234 loaded=1761400012 jobs=17 threads=4 edits=3 elapsed_ms=553210 written=1000
skipped=3 stopped=0 failed_index=- failed_stage=- output_failed=0
```

| Key | Source |
|---|---|
| `protocol`, `commit`, `dirty` | The harness's build (`dirty` is `-` with an `unknown` commit) |
| `build`, `slice`, `translated` | `game_timestamp` (the game's bundle version), `game_architecture` and `game_translated` (Rosetta) |
| `pid`, `loaded`, `jobs` | The game's process, when the harness loaded (`job_markLoaded`, seconds since 1970), and the jobs other than `status` it has received since, this one included, whether it ran them or refused them (`job_count`) |
| `threads`, `edits`, `elapsed_ms` | Workers started, the input's edits re-applied per seed (`-` with `--keep-build` or the input's own seed), and the job's time |
| `written`, `skipped`, `stopped` | The places written (played or skipped), those skipped, and `1` if the stop file kept a seed from starting |
| `failed_index`, `failed_stage` | The first place in the list whose failure stopped the job, as `index_base + place`, and `rebuild`, `deserialize` or `stats`; `-` for none. Unless a file could not be written, the rows stop there: it is the index after the last place written |
| `output_failed` | `1` if a file could not be written |

The longest line a job can give fits in a reply (512 bytes). The `job_run`
suite checks one with every field at its longest: 11 digits for counts of
seeds (what a 16 KB job can list), 13 for jobs, edits and milliseconds, and
any 64-bit index.

## Run manifests (`fm24-run-manifest/1`)

`fm24ctl run --manifest` sends `report=1` and writes `<stem>-manifest.json`
([Run manifests](CLI.md#run-manifests) lists its keys). `commands.c`
gathers the facts and `manifest_formatRun` (`src/runner/manifest.c`) only
formats them, so tests give it their own clock and host:

- **The report.** `runReport_parse` (`src/runner/run_job.c`) reads the
  suffix above: every key once, in order, with values the harness can
  write (`dirty` is `-` exactly when the commit is `unknown`, and
  `failed_index` and `failed_stage` are both `-` or neither). Anything
  else is no report, and the manifest's `harness` is `null`. The `runner`
  suite parses the longest and the plainest lines `job_run.c` writes.
- **The wait.** `run` submits with `client_submitWatched` (`client.h`),
  which says how the wait ended and when the harness took the job: no
  harness serving, or one that closed the connection before taking the
  job, is `no_harness`; time running out before it took the job is
  `queue_timeout`, and after, `run_timeout`; a closed connection or an end
  without a reply once it had taken the job is `lost`. Its ticks, every
  `tickMs` while it waits (connecting, queued or running), can stop the
  wait (`abandoned`); `run` has none. `client_submit` is the watched call
  without a watch, with the same messages.
- **The outcome** (`manifest_runOutcome`): `not_submitted` unless the
  harness took the job; `ok` for a successful reply; `stopped` when the
  report says the stop file stopped the job and nothing failed or went
  unwritten; otherwise `error`.
- **The files.** `manifest_readOutput` reads each output once: its size,
  rows (complete lines after the header) and SHA-256 and, for the results,
  the SHA-256 without each line's last field (`content_sha256`) and the
  summary. They are read only when the reply has a report, which the
  harness gives after opening them for this job. The fixture's hashes come
  from the bytes `run` reads and encodes anyway, and its header from
  `matchConfig_readHeader`, which `matchConfig_readOrigin` now uses too.
- **The computer and the game.** `hostInfo_read` reads `hw.model`,
  `machdep.cpu.brand_string`, `hw.logicalcpu`, `hw.perflevel0` and
  `hw.perflevel1.physicalcpu`, `hw.memsize`, `kern.osproductversion`,
  `kern.osversion` and `sysctl.proc_translated`
  (`host_info_macos.c`).
  `macosGame_residentBytes` gives the game's `ri_phys_footprint`
  (`proc_pid_rusage`), Activity Monitor's Memory.
- **Sleep.** `slept_ms` is the monotonic clock's time over the wait less
  the uptime clock's (`platform_uptimeTicks`), which stops while the Mac
  sleeps; a difference under a second counts as the clocks' drift.
- **Writing.** `files_replace` (`src/common/files.c`) writes a temporary
  file beside the manifest, syncs it (`platform_syncFile`), renames it over
  the manifest (`platform_replaceFile`) and syncs the folder. Before the
  job, `run` checks the manifest's folder as for that new file, and that
  it is not append-only, which would take the new file but not the rename
  (`paths_folderAppendOnly`), and the manifest itself only for being a
  folder or locked (`checkManifestPath` in `commands.c`), with the other
  outputs (see
  [the CLI reference](CLI.md#requirements-and-conventions)).

`harness_matches_fm24ctl` compares the report's protocol, commit and dirty
flag with `fm24ctl`'s own (`build_info.h`), and `run` warns when they
differ: a game keeps the harness it loaded until it restarts, and an older
build of the same protocol answers without saying so. Two builds of one
commit with different uncommitted changes still look the same.

## Batches (`fm24-batch-plan/1`)

`fm24ctl batch` ([Batches](CLI.md#batches-batch) has the commands and
files) keeps all of a batch's state in its folder, and changes it so that a
process stopped between any two steps, then started again, still ends with
every planned index in exactly one committed chunk. `batch_store.c` keeps
the folder, `batch_verify.c` reads the rows, `batch_plan.c` reads plans and
makes seeds and jobs, and `batch.c` runs the commands. Only the process that
holds the batch's lock changes it (`batch run`); reading needs no lock.
`batch_run.c` plays a batch and `batch_policy.c` decides what to do when
something goes wrong (see [`batch run`](#batch-run)).

**Seeds.** `batchSeeds_scatter` is
`lowbias32(lowbias32(index ^ low(k)) ^ high(k))` with `k = splitmix64(key)`,
a bijection on 32-bit indices: the `batch` suite inverts it over a million
indices. Mixing the key in twice, rather than once, matters: with
`lowbias32(lowbias32(index ^ key))` adjacent keys would play the same seeds
in another order, and the suite checks that keys 20261025 and 20261026
share only about as many of a million seeds as chance gives.

**State.** A chunk is committed once its `chunk.json` exists. Each job at a
chunk is an attempt, `attempts/<arm>/<chunk>/a<k>/`, whose `attempt.json`
(the indices it was given, its seeds' and job's SHA-256, threads, session
and start) is written and synced before the job goes to the harness. When
the job ends, the verifier finds its part and `part.json` records it,
written in one step: how many indices it covers (`verified`), the outcome
(`ok`, `stopped`, `crashed`, `abandoned`, `adopted` or `error`), the
result line, times, rows and an optional `poison` index. The harness only
flushes the attempt's files, so they and their folder are written through
to the disk before `part.json` is, which never vouches for rows the disk
has not been told to keep. `batch.json` and
`index.csv` are made again from these files; nothing else is kept.

**The verifier** (`batchVerify_run`) reads a part's four files in one
forward pass. Each must start with its header. Then, for each index from
the part's first: the next failed row covers it if it is for that index
(failed rows must be complete, ascending, within the part and of the
planned seed, or they end there); otherwise the next results row must be a
complete line of 7 fields with the planned seed, and with per-match rows
the next two team rows (home then away, 44 fields, the same index and
seed) and each side's `squad` player rows (slots 0 up, 62 fields, the
team's `team_uid`, values present exactly when the player appeared). The
first index that fails ends the part. A torn last line, a zero-filled tail
left by a power cut, and per-match rows written ahead of their results row
(the harness's first write step, see above) do not count. Seeds are
distinct within a set, so a missing failed row shows as the next results
row's seed not matching. A committed chunk's files are checked the same way
(`--deep`), with each result row's index first and `chunk.json`'s excluded
indices covered without rows.

**The chain.** From a chunk's first index, the part that starts at the
cursor and advances it furthest (its `verified`, and one more if its
`poison` is the index after them), the latest of equals, moves the cursor
on; a part with a poison mark there makes that index excluded. The work
left is from the cursor to the chunk's last index. A part that starts
where the chain never stops is stale and is removed. The next attempt
starts at the cursor, and only once every earlier one has its `part.json`,
so the parts form one chain. `batch_finishAttempt` records a poison index
only when the attempt crashed (or was quit after a hang) exactly there, so
`batch run` can pass the index where the previous attempt stopped without
knowing in advance where this one will, and an attempt that played nothing
without a crash (a busy game, a stop before its first match) marks
nothing.

**Commit** (`batch_commit`), once the chain covers the chunk:

1. Merge each chain part, verified again up to its `verified`, into
   `chunk=<first>.tmp/`, giving each result row its index and noting the
   rows, sizes, SHA-256s and the results' `content_sha256` as they are
   written.
2. Compress each file (`gzip -n -6`, checked with `gzip -t`) and hash it.
   gzip runs without the `GZIP` environment variable, whose options (such
   as `-k`, which keeps the uncompressed file) it would add to these.
3. Write `chunk.json`.
4. Write each file and the folder through to the disk (`F_FULLFSYNC`).
5. Rename the folder to `chunk=<first>`, and write its parent through.
6. Remove the chunk's attempts, then add the chunk to `index.csv` and
   `events.log` and rewrite `batch.json`.

A process stopped before the rename leaves the attempts and a `.tmp` folder,
which the next start removes before committing again; one stopped after it
leaves the committed chunk and attempts the next start removes. A power cut
can lose only what step 4 or 5 had not written through, which again leaves
the attempts, so no index is lost or counted twice. A commit that fails
before the rename removes its `.tmp` folder.

**Recovery** (`batch_recover`, the start of every `batch run`, once no job
is still writing) removes the `.tmp` folders, `chunk=` folders without
`chunk.json`, attempts that never wrote their `attempt.json`, and the
attempts of committed chunks; evaluates each attempt without `part.json`
(as crashed, or adopted if `batch run` saw its job finish); verifies each
part again and shortens one whose files now cover fewer indices than its
`part.json` says (a disk that lost what it was told to keep), rewriting
`part.json` and logging `part_shortened`, so that its chunk plays on from
there; removes stale parts; logs `chunk_committed ... recovered=1` for
committed chunks that `events.log` lacks, reading it by its length, so that
the lines after a tail a power cut left as zeros count and each chunk is
logged once; rewrites `index.csv` whole; and
commits every chunk its parts now cover, except an arm's chunk 0 when the
plan has canaries, which `batch run` commits in its loop so that it is
compared with the reference. Appends start on a new line, so a line torn by
a stop stays on its own.

**Atomic writes.** `attempt.json`, `part.json`, `index.csv`, `batch.json`
and `plan.txt` are written as a `.tmp` file beside them, synced, renamed
over them and their folder synced (`batch_writeFile`), through the host so
that the tests count the syncs instead of waiting for them.

**Tests.** The `batch` suite runs batches against a fake host (its
"compression" changes every byte, its syncs are noted, and its clock stands
still) and a fake game that writes each attempt's files as the harness
would, with the harness's own row formatter (`matchStats_formatRows`):
crashes partway with a torn line and a zero-filled tail, one that crashes
at once, seeds that fail to rebuild and a seed that crashes the game every
time. The host's `reached` hook stops the "process" after any step of any
change. The suite kills a run after each of its 135 steps in turn, and
again every 11, 13 and 17 steps until it finishes, tearing lines of
`events.log` and `index.csv` and leaving a temporary `batch.json` after
each kill. Each run must end with every index of both arms in exactly one
committed chunk with its own seed, files that `--deep` verification
accepts, the same chunk contents as a run without kills, `index.csv` as
the chunks make it, and one `chunk_committed` for each chunk, each on a
line of its own. A listed, uncompressed batch without per-match rows is
killed after each of its 68 steps too.
It also checks that a chunk's files and folder are synced before the
rename that commits it, and the rename before its attempts are removed.

### `batch run`

`batchRun_run` takes `batch.lock` (`flock`, as the harness locks its
socket), opens the batch (checking `plan.txt` and the inputs), starts
`caffeinate -w <pid>` and the signal handlers, and then makes the folder
consistent before playing anything. The host starts `caffeinate`, `gzip`,
`pmset` and `osascript` each in a process group of its own
(`POSIX_SPAWN_SETPGROUP`), with `SIGTTIN` and `SIGTTOU` blocked so that
they still write to the terminal: Ctrl-C goes to the terminal's foreground
group, and in fm24ctl's it would also end `caffeinate`, which would stop
keeping the computer awake, and a commit's `gzip`, failing the commit,
while fm24ctl's handler only asks for a stop. `macos_game.c` starts `open`
the same way, and waits for it through the signals fm24ctl's handler
takes. The host's programs get only the standard input, output and error
(`POSIX_SPAWN_CLOEXEC_DEFAULT`): a `gzip -dc` that held the pipe of
another would keep that one from ending (`SIGPIPE`) when `verify --deep`
stops reading it early, and closing it would wait indefinitely.
`caffeinate -m -s` keeps the computer awake on AC power only, so that it
can sleep while the batch pauses on battery power; with
`pause_on_battery=0` it also gets `-i`, which holds idle sleep off on
battery power too.

1. **The barrier.** Only the holder of the lock submits the batch's jobs,
   so a job still running in the game is one a stopped `batch run` left.
   If an attempt has no `part.json` and the game's harness is serving,
   `run` asks for the game's status with a 10-second wait until the
   harness answers (it is free, and the job ended: the attempt is
   *adopted*), the game goes (*crashed*), a stop is asked (below), or
   `queue_wait_minutes` pass, watching the attempt's files meanwhile as the
   watchdog does. `control/stop` is removed before the barrier, as it asked
   the stopped run. A `control/stop-now` it left is kept for its job, which
   stops at it, and removed only once the barrier is over; `run` keeps its
   bytes, and only a `stop-now` with other bytes asks this run to stop.
   `batch stop` writes a line of its own into each (`pid=… ticks=…`); the
   signal handler only creates a missing file, and its signals are counted.
2. `batch_recover` (see above) with the barrier's outcome for unevaluated
   attempts.
3. An arm's committed chunk 0 whose `chunk.json` records a mismatch with
   the canary reference, but which `suspect.csv` does not list (its run
   stopped between the commit and acting on it), is listed now and
   `on_canary_mismatch` applied. Lines a power cut left as zeros are
   passed over (lines are read by the file's length, not as a string), so
   a line added after them counts, and the line is written through to the
   disk, so the next run does not act on it again. The tools count such a
   chunk as suspect from its `chunk.json` in the meantime.

**The loop**, while a chunk of the plan's order is not committed: commit
it if its chain covers it; else stop if asked (`stop-now` at once;
`stop`, the first signal, `--until` and `--max-chunks` only between
chunks); check the free space and power; make sure of the session, without
starting the game while a stop is asked; check for a stop again, as the
save check and a session's warm-ups and canaries take a while; then play
one attempt, record its part, and act on the policy's decision.

**Sessions.** `macosGame_checkSave` (`macosGame_ensureSave` with how the
wait ended, so that a busy game is told from another save) takes a
`SessionNeed` with the batch's `savePath` (a `.fm` file to start the game
with), `rosetta` (`slice=x86_64`), `readyS` (`busy_wait_minutes`) and
`stop` (`SessionStop`), which `askedStop` answers. While the check waits,
between its samples a second apart and on its status queries' ticks
until the harness takes them, any stop ends it (`SESSION_STOPPED`, exit
`4`): no job of the batch's has started. A check its first sample decides
is not stopped, so a stop with a chunk under way lets the attempt play;
the wait of a game being started for its harness is not stopped, and one
stopped while the started game loads the save leaves its auto-play file. A
game process other than the session's starts a new session; so does a
report whose `pid` or `loaded` differs from the session's (the game
restarted under the batch), in which case the attempt's rows are left out,
as is an attempt whose report shows a harness change not allowed. The
warm-up is there because `seedBuilder_open` finds a fixture's edits by
comparing it with a build of its own seed: in a session's first job that is
the first build after the load, which differs at `+0x46` and may order a
club's players differently (see [Known limits](#known-limits)),
so a fixture exported right after a load could get another set of edits in
each session's first job than in later ones. The batch's own jobs since the
session's last report are counted (status jobs aside, as the harness counts
them): a report with more jobs than that means another runner's jobs ran,
which may have built matches, so the canary runs again before the next
chunk.

**The watchdog** is the client's tick (`client_submitWatched`), every five
seconds: the game's process must be running and its harness must hold its
lock. A process that is exiting, or has exited but is not yet reaped,
does not run (`sysctl`'s `P_WEXIT` and `SZOMB`), and a game whose harness
has gone has 10 seconds (`BATCH_EXIT_GRACE_S`) to exit before it counts as
running without its harness: the kernel closes an exiting process's
connections and frees its lock before its process ID goes, so the client
sees the connection close while the process still seems to run. The
attempt's results and failed seeds must grow within
`hang_minutes` once the job is taken, measured on the uptime clock
(`CLOCK_UPTIME_RAW`, which stops while the Mac sleeps), and a gap of more
than 30 seconds between the monotonic and uptime clocks is sleep: logged,
added to the part's `slept_ms`, and the hang timer starts again. Rows are
written as an in-order prefix, so one stuck worker stops growth while the
others still play. Waiting to be taken is not timed by the hang timer;
`queue_wait_minutes` limits it. After a hang without `kill_game`, `run`
waits for the job as the barrier does and adopts what it played; a game
quit meanwhile has the same 10 seconds to exit, and counts as crashed.
Giving up after `queue_wait_minutes` is its own outcome
(`BATCH_WATCH_GAVE_UP`, an abandoned job with the game running and
serving), which stops with `1` and says that the job may still run. The
status queries of these waits are quiet (`ClientWatch.quiet`): the client
does not say that it waits behind another job.

**Stops.** Every tick, the 200 ms ticks of the status queries included,
reads the signal count and the control files (`askedStop`): the first
signal or `stop` asks for a stop after the chunk, the second signal or a
`stop-now` (other than the barrier's stale one) for a stop now. A stop
asked during a status query ends it, so that the wait acts at once, and
`waitForJob` checks again after each five-second wait, before its next
status query, which a hung job would hold for 10 seconds. Before
the harness takes a job, any stop abandons it: the client sends the job
only once it is taken, so the harness never runs it. Once a hang is noted
any stop ends the wait for the job, and a job asked to stop now that has
not grown for `BATCH_STOP_NOW_GRACE_S` (30 s) since is not waited for any
longer (`BATCH_WATCH_STOP`). With `kill_game=0`, `run` then exits with `4`,
leaving the job running and its attempt without `part.json` for the next
barrier, and prints and notifies the game's process ID. A warm-up, canary
or lookup has no part, and the barrier does not wait for one: the next
run's save check and first job wait behind it as behind another runner's,
and `run` says so; with `kill_game=1`
it quits the game, and the crash that follows stops. The policy's state
carries the stop asked, so that a decision that would start the game again
(relaunch, retry with one worker, a poison seed) stops with `4` instead,
with `launch=0` too; limits that stop with `1` still do. `ensureSession`
does not start a game that is not running while a stop is asked.

**FM24's logs.** With `trim_game_logs=1`, `run` calls the host's
`trimGameLogs` in `loop` before its first attempt (after the stop check at
the boundary, and before `checkHost`, so that the free-space check sees the
space it freed) unless `commitChunk` has trimmed already
(`trimGameLogsFirst`, by `Run.gameLogsTrimmed`), and again in `commitChunk`
after each commit: so between jobs, never while one of the batch's runs, and
never in a run that plays no chunk, such as a complete batch's run or one
that a stop or `--until` ends before its first chunk. The host's trim is
`gameLogs_trim` (`game_logs_macos.c`) on `<data>/Logs`, where `<data>` is
`macosGame_dataFolder`: the folder `dataFolder` gives a save lookup without
`--user-data`, the one Steam's launch option gives the game with
`user_data_location` when `launchOptionSet` finds the launcher in it, else
the usual one, so the two cannot disagree. A game started directly, by
`launch` with an `fm.app` path, gets the usual folder whatever the option
says, and its logs are then not the ones trimmed. `gameLogs_trim` opens the
folder once (`O_DIRECTORY`; a missing one, `ENOENT`, is nothing to do) and
uses every entry through that descriptor: `fdopendir` on a duplicate,
`fstatat(..., AT_SYMLINK_NOFOLLOW)`, `unlinkat` and `openat`, so nothing
outside the folder is reached, whatever happens to its path. Only regular
files (`S_ISREG` of `lstat`) named `file llist errors_` + anything + `.txt`,
case counting, are listed; links, folders and the rest are left, and
subfolders are not read. If the folder cannot be read to its end, nothing
is trimmed. The newest by `st_mtimespec` (then by name, which holds the
date and time) is FM24's current log: it is opened with `O_WRONLY`,
`O_NOFOLLOW` and `O_NONBLOCK`, checked to be a regular file with `fstat`, and
truncated with `ftruncate(0)` if it is not empty. Truncating rather than
deleting frees its space while FM24 holds it open: its next write lands at
offset 0 if it appends (`O_APPEND`), or at its own offset after a hole,
which APFS does not store (a 64 MB test file took 4 KB after such a write;
`st_size` stays large). A deleted file FM24 still held would free nothing
until FM24 closed it. Each truncation sets the log's modification time, but
FM24's next session starts a log written later, so the newest is still
FM24's. The others are deleted (`unlinkat`); one that vanished meanwhile
(`ENOENT`) is passed over quietly, as is a newest log that became a link
(`ELOOP`). `freedBytes` adds up `st_blocks * 512` of each log emptied or
deleted. Failures come back as text, by kind (`GAME_LOGS_FOLDER`, `_READ`,
`_EMPTY`, `_DELETE`), the first of each kind a trim met; `run` logs and
prints each kind once a run (`Run.gameLogsWarned`) and goes on.

**The policy.** `batchPolicy_decide(state, event)` is a pure function of an
event (a job that ended, with its client outcome, watchdog stop, reply and
part; the save check; the slice; the date; an identity change; a canary;
seed errors; the disk; the battery) and what the batch knows (the plan,
crashes in the last hour, the arm's poison seeds, how long the game has been
busy, failed starts, and the stop asked). It returns continue, retry, retry
with one worker, mark poison, relaunch, wait, quit and relaunch, or stop
with an exit code, and the reason that goes to `events.log`, `batch.json`
and notifications.
`batchPolicy_shape` makes the next attempt from a chunk's parts: after two
crash-like parts in a row, the second having played fewer indices than it
had workers, one worker over as many indices as it had workers; after a
crash with one worker, one worker over just the index it crashed at, offered
to `batch_finishAttempt` as the poison candidate. Attempts at the end that
neither crashed nor played anything are passed over, so the candidate is
offered again after a busy reply. A crash of an attempt shaped this way is
logged with `isolating=1` and neither counts toward `max_crashes_per_hour`
nor is stopped by it: isolating one seed takes four crashes, which would
otherwise use up the default limit, and `max_poison` bounds them. Each case
of the [failure table](CLI.md#when-things-go-wrong) has a test.

**Canaries.** The reference is the first session's canary output, copied
to `canary/` (the results last, which marks it whole). A canary matches it
if every file has the same rows after its header, the results without their
last field (`ms`). When an arm's chunk 0 commits, its merged files are
compared before compression (`BatchCommitFacts.checkCanary`), rows from its
first index up to `canary` indices on, without the results' `index`.

**Tests.** The `batch` suite runs `batch run` against a fake host and a
fake game (the harness's job parser, its files and report as in `run`, and
faults at an index: a crash with a torn row, a crash the watchdog sees, a
crash whose process is still seen as it exits, a hang, sleep, a busy game,
a third signal, `stop` and `stop-now`, an unsupported build, the harness
going, another runner's jobs, a failing seed, the game quit while `run`
watches a hung job and its process seen for 9.7 or 15 seconds after), and
`batch stop`, `batch stop --now`, signals as the handler takes them and the
game quit, at a time after a hang, at a status query, at a power check or
at an uptime, with a job left running that hangs or stops at its stop file,
a save check that waits behind another runner's job, on
clocks that move only when the fake game plays or `run` waits (in steps of
100 ms and the client's ticks where a test needs the real timing), with part
files cut short after their `part.json`, and `suspect.csv` and `events.log`
ending in zeros, as a power cut can leave them. Each case ends with every
index once, and the runner killed after each of its steps and started again
ends as an uninterrupted run, with each arm's chunk 0 compared with the
reference and listed in `suspect.csv` when it differs. FM24's logs are
trimmed in a test folder (by the fake host, with the fake game
adding to the session's log for each seed it builds): once before the run's
first chunk and after each of its chunks; nothing with `trim_game_logs=0`,
without a `Logs` folder, in a complete batch's run or in one that `--until`
stops before its first chunk; and each kind of failure, real (a folder that
cannot be changed) or reported by the host, logged and printed once a run
while the batch plays on. `gameLogs_trim` itself is checked on a folder
with logs of several ages, names that only nearly match, a folder named as
a log, a log in a subfolder, links named as logs to a file outside the
folder and to nothing, the newest held open for appending and for writing
at its offset, a missing folder, a file in its place, a folder whose
entries cannot change and a newest log that cannot be written.

The `macos` suite runs the real host's client, socket, save check, gzip and
syncs against the stand-in harness serving a test socket on a thread of the
test process, with faults: the game exiting mid-job with the connection
closed and no reply, a busy game, a stalled job watched and adopted or quit
with `kill_game=1`, another save, `stop-now`, a stalled job stopped by
`batch stop`, `stop --now`, the real signal handler and a quit, and the
save check waiting behind a warm-up a stopped run left, stopped the same
way (with the host's log trimming left out, so that it never reaches the
home folder the suite runs in); the host's trimming in a test home folder:
in the usual data folder, in the one a launch option with the launcher
gives, in the usual one for an option without it, and nowhere for an
option `fm24ctl` does not follow; and the host's `pmset`, `caffeinate` and
`osascript` calls, recorded instead of run, each in a process group of its
own with only the standard descriptors, a decompression closed early while
another is open, `open` in a group of its own with a handled signal arriving
while it runs, its signals, `macosGame_stop` against a stand-in for the
game's process (one exiting without a path among them), and an exited
process its parent has not reaped, which does not count as running.

### Season batches

A season batch (`mode=season`) is a batch whose arms are a league's
fixtures and whose indices are seasons, so that it reuses the store, the
verifier, the chain, commits, recovery, sessions, the watchdog and the
policy unchanged. `batch_season.c` holds what is its own and pure.

**Fixtures.** The parser makes the arms from the `team` lines: fixture *k*
of *n* teams is team ⌊*k* / (*n* - 1)⌋ at home to the *k* mod (*n* - 1)th
of the others, `f%04u` of *k* + 1, with its teams' unique IDs in
`BatchArm.pair`. Arms live on the heap (`BatchPlan.arms`, freed with
`batchPlan_free`): at most 16 for a match batch, 1,560 for 40 teams. The
frozen plan adds `mode`, `base`, the `team` lines, `base_fixture` (the
base's hashes and overrides, as an arm's `fixture` line) and a `pair`
line for each fixture, which the reader checks against the teams; a match
plan writes none of them, so its frozen text and `plan_sha256` are as
before (the suite has its golden). The fixtures' hashes and overrides are
not known until they are built, so they are in `inputs/fixtures.txt`,
which `batch_open` reads into the arms; until it is there, a committed
chunk or an attempt makes the batch changed. `jobBase` sizes a season's
jobs with the longest overrides, which fit as 10 digits each.

**Seeds.** `BATCH_SEEDS_SEASON` has a `stride`, *F*, and an `offset`, *k*:
`batchPlan_armSeeds` gives each arm its set, the plan's for a match batch,
and every place that took the plan's seeds takes the arm's (the attempt's
job, the verifier, `chunk.json`, poison seeds, warm-ups and canaries).
`scatter` is a bijection on 32 bits, so the *s* × *F* + *k* below 2^32 that
the plan allows never repeat a seed within a batch; the suite checks the
380,000 of 1,000 seasons of 20 teams, and shares its goldens with
`fm24seeds.py`.

**The build** is `buildFixtures` in `batch_run.c`'s loop while
`Batch.fixturesFrozen` is false: one step at a time, each after
`stopAtBoundary`, `checkHost` and `ensureSession`. A session started
during the build warms up the base rather than the arms
(`warmUpArms`), so that no replacement is its first build, writes the
lookups, and runs no canary. `Run.homesBuilt` restarts with each session,
so every session rebuilds each team's home intermediate before any fixture;
`Run.fixtureCursor` moves past fixtures whose JSON is in place
(`batch_fixtureBuilt`). A replacement is a job like a warm-up (no part):
`judgeJob` handles a crash, hang or busy game, and an `error:` reply, or a
success `batchSeason_checkReply` or `batchSeason_checkBuilt` refuses,
stops with `1` (`buildFailed`). `batch_keepBuilt` writes the encoding with
`batch_writeFile`, compresses the JSON (the host's gzip) and renames it
into place, written through to the disk (`BATCH_STEP_FIXTURE_BUILT`), so a
fixture is built exactly when its JSON is there, and a `.bin` without it
is built again. `batch_freezeFixtures` hashes each `.bin` and each JSON
decompressed, reads the overrides from its header, writes `fixtures.txt`
(`BATCH_STEP_FIXTURES_FROZEN`) and removes `inputs/build/`; `run` then
sets `needsWarmup` and `needsCanary`, so that the session warms up the
check fixtures and runs their canaries before the first chunk. Recovery
removes the build's `.tmp` files from `inputs/` and `inputs/build/`, or
all of `inputs/build/` once frozen.

**Check fixtures** (`batchSeason_isCheckFixture`, through
`batchPlan_isCheckArm`) are the pairs (t0, t1), (t2, t3) and so on, with
(t(n-1), t0) when *n* is odd: every team once, so each club's first build
of a session is a warm-up's, as the canaries' comparison needs. Only they
are warmed up and have canaries and a canary reference, so only their
chunk 0 is compared with it.

**The edits check.** A fixture is the build of its own seed, so each
rebuild should find no edits. An attempt or canary whose report has
`edits` other than 0 (`playedEdited`) is discarded
(`BatchPartFacts.discard`) and stops the batch (`BATCH_EVENT_EDITS`, `1`);
warm-ups are not checked, as their first builds are why they run.

**Progress.** `batch_seasons` counts a block complete when every fixture's
chunk of it is committed, and adds up the failed and excluded seeds of
complete blocks; `commitChunk` logs `seasons_complete` when a commit
completes its block. `batch_armTotals` finds an arm's chunks by binary
search, as `writeArms` adds up every fixture's after each commit.

**Tests.** The fake game answers `replace_home` and `replace_away` as the
harness does, writing a fixture whose encoding holds its two teams (and
an override only for a team other than the base's own on that side), and
names a season fixture's teams in each run job's per-match rows, so that
`verify --deep` checks them. The suite builds and plays a 3-team season of
4 seasons in blocks of 2, killed after each step of the build and the
chunks in turn, and from every fifth step again every 11, 13 or 17 steps
until it finishes, each ending as the uninterrupted run; a crash, an `error:` reply, a kept edit, another
override and another date at given replacements, a stop and `--until`
between them, and what a stopped build leaves; and a report with
`edits=2` in an attempt and in a canary. The `macos` suite builds and
plays one over the stand-in harness's socket with the real gzip.

## Match configs (`fm24-match-config/1`)

`fields` lists every write the game's serialiser makes, in order, so encoding
is lossless. The encoder reads only `format` and each field's value; every
other key is an annotation, except `home_team` and `away_team` (unique IDs of
teams substituted for the fixture's original sides), which `run` passes
to the harness. `site`, `p`, `member` and the header's `paths`
and `bytes` are written only with `get-next-fixture --full`. Exports and
team replacements also write `save` and `game_date` after `source`: the
save name and in-game date of step 7, each only when it can be read.
`decode` never writes them. `fm24ctl` reads them back
(`matchConfig_readOrigin`, a pass over the top-level keys only): `run`,
`replace-home`/`replace-away` and `inject-player` with an ID first wait for
the game to have `save` loaded and idle, or start it with that save, and
`run` warns when the save's date is not `game_date` (`session_plan` and
`macosGame_ensureSave`; see `docs/CLI.md`). User-facing field meanings are
in `docs/FIXTURE.md`.

- **Value:** each field has exactly one: `u8`, `u16`, `u32`, `u64`, `str`
  (u32 length + UTF-8), `hex`, or `u8map`.
- **Location** (`--full`): `site` gives the `<call site>/<caller>` of the
  write as Windows Steam build RVAs, after the
  [build tables](#build-tables)' translation (named parts are in
  `src/dll/sites.h`); a frame without a Windows counterpart appears as
  `0x80000000 | macOS offset`. `p` indexes the `paths` table of serialiser
  call chains.
- **Seed:** the seed field has `"role": "seed"`.
- **Labels:** blocks carry a `"name"` (`match`, `referee`, `venue`, `fixture`,
  `home.player[3]`, `away.manager`, `home.backroom[2]`, ...), and player
  blocks also carry `"player"`. Fields whose meaning is known are named too:
  `.person_uid`, `.ratings`, `.ability` (caps every role rating),
  `.leadership_value`, `.role_rating[winger@AMR]` with its `.role` and
  `.position` bytes, and the team counts and flags. The weather
  (`match.weather.*`), the venue's fields (`venue.pitch.*`, `.stadium.*`,
  `.attendance`, `.stand[i].*`, `.section[i].*`, ...) and the attendance's
  copies in `fixture` and `fixture_extra` are named by write site or member
  (`labelVenueField` in `src/dll/labels.c`, sites in `src/dll/sites.h`).
- **Tactics:** each manager's tactic is under `<side>.manager.tactic`. It
  holds `takers`, the active `plan[0]` and a second `plan[1]`,
  `set_pieces`, and `formation[i]`. A plan names `.mentality` (1-7),
  `.team_instructions[0..2]` and each formation slot's `.slot[i].position`,
  `.slot[i].role` (role bit plus a duty bit) and
  `.slot[i].player_instructions[role].bits[0..1]`.
- **Members** (`--full`): most fields also carry `"member"`, the game object
  member the serialiser wrote, named as in the Windows build, where the
  original project found them in IDA: `MATCH_PLAYER_DATA+0x60`,
  `FIXTURE_RESULT+0x46`, ... Unnamed serialisers appear as `fn_<rva>+0xNN`;
  `STRUCT[element]` is an array element, `(computed)` a value the serialiser
  calculated (a count or flag) and `(constant)` a fixed byte. All of these are
  annotations; the encoder ignores them.
- **Ratings:** each player's ratings are a `u8map`: 15 positions (1-20),
  then 54 attributes (1-100 = in-game value x 5), named in
  `src/dll/labels.c`.

Values and strings (including their length) can be edited freely. Adding or
removing entries changes the structure and is not safe yet. Edited ratings
can be played as they are: the engine plays from the raw attributes, and the
values the game derives from them (ability, role ratings) don't affect
results.

# Known limits

- Only the Steam build 24.4.2 (2081827), both slices, is supported; the
  harness refuses any other ([macOS limits](MACOS.md#known-limits)). A new
  build needs a new mapping (see [tools/macos](../tools/macos/README.md)).
- With `--keep-build`, patching the seed in an input is not the game
  choosing that seed: pre-match data (attendance etc.) also depends on the
  build-time RNG.
- Rebuilding per seed needs the input to be the human manager's next
  fixture, in the same game state; once the match is played in the game,
  use `--keep-build`.
- One input = one fixture with fixed line-ups and tactics.
- A game-produced .bin and its JSON export differ in one header byte (offset
  21, a flag the deserialiser sets). Match results are identical.
- `get-next-fixture` (and every per-seed rebuild) sets one byte (`+0x46`) of the real
  fixture in the save and leave it set, as the game's own match setup
  probably does. The first build after loading a save therefore differs in
  that byte from later builds with the same seed. The byte before it,
  `FIXTURE_RESULT+0x45`, can change too.
- Building a match has the game pick the match's observers, the people
  attending to watch players (mostly national-team managers;
  `GAME_MATCH+0x720`, written by `GAME_MATCH__serialize_base`,
  `ObserverPart` in `src/dll/sites.h`), when its match-day options and the
  fixture allow. `GAME_MATCH__init_from_fixture` books most of them in the
  game's matchday manager (`[RVA_HUMAN_MATCHES_HOLDER]`, a list at
  `+0x170`) and passes over booked people in later builds until the game
  resets that list. The harness doesn't undo the bookings. So the first
  build of a pairing can list an observer that later builds don't, and
  which observers a seed's build lists depends on the builds before it,
  including the order in which worker threads reach them. Whether the
  engine reads the observers is not known. Per-seed rebuilds and team
  replacement leave the observers out when they compare an input with the
  game's build (`findEdits` in `seed_build.c`) and when they split a build
  into parts to align it with the input; they are never edits, so each
  build keeps its own.
- The game doesn't always list a team's players in the same order. A team's
  26 player slots (`MATCH_TEAM+0x180`; the count at `+0x3d2`) are filled on
  every build from the line-up the AI picks for an AI side, and for the
  human side before the team is submitted. Players it rates alike can then
  come out in either order: with another seed or opponent, and between a
  club's first build after the game starts and later builds, which agree
  with each other (4 of 13 clubs tried on one save, alike in both sessions
  checked). What the first build changes is not known; it is not the
  seeded RNG, nor a re-sort of the previous build's order. The
  order changes the match: two files that differ only in the order of two
  substitutes gave other results for each of 100 seeds, with the same
  spread overall. Per-seed rebuilds and team replacement therefore pair
  players by person: when the input is opened, its players are paired with
  those of the build of its own seed by their writes and then by how many
  records they share (`comparePlayers`), and each rebuild's players are
  paired with them by unique ID (`alignPlayers`). Edits, injected players
  included, follow each player, and a build that leaves out an edited
  player fails. A file exported from a club's first build keeps its order
  when played as it is (`keep` or `--keep-build`). References to a place in
  a list, such as the marked opponent's index, are not adjusted, except by
  `lineup`, which moves whole blocks offline and points the other side's
  marking of a moved player at its new place.
